# Equipment Tracker

API учёта выдачи рабочего оборудования сотрудникам. Хранит сотрудников, предметы оборудования и выдачи (кому, что и когда выдано и вернули ли). Данные лежат в PostgreSQL, API написан на FastAPI.

Правила предметной области:

- предмет нельзя выдать двум людям одновременно;
- у одного сотрудника не больше трёх активных выдач;
- неактивному сотруднику нельзя выдавать оборудование;
- сотрудника с активными выдачами нельзя деактивировать;
- вернувшийся предмет можно выдать снова.

## Версии

- psycopg 3.3.6 (синхронный, `psycopg-binary`)

## База данных

Создать базу и применить схему:

```bash
createdb equipment_tracker
psql -d equipment_tracker -f schema.sql
```

Строка подключения берётся из переменной окружения `DATABASE_URL`. Пароль в репозиторий не коммитится, `.env` в `.gitignore`.

```bash
export DATABASE_URL="postgresql://ПОЛЬЗОВАТЕЛЬ:ПАРОЛЬ@localhost:5432/equipment_tracker"
```

Без `DATABASE_URL` приложение при обращении к БД падает с понятной ошибкой `RuntimeError`. Служебная ручка `/health` базу не использует и работает без неё.

## Маршруты

| Метод | Путь | Что делает | Успех | Ошибки |
|---|---|---|---|---|
| GET | `/health` | Проверка, что приложение запущено | 200 | — |
| POST | `/employees` | Создать сотрудника | 201 | 409 (email занят), 422 |
| GET | `/employees` | Список сотрудников | 200 | — |
| GET | `/employees/{id}` | Один сотрудник | 200 | 404, 422 |
| PATCH | `/employees/{id}/deactivate` | Деактивировать сотрудника | 200 | 404, 409 (есть активные выдачи) |
| POST | `/equipment` | Создать предмет | 201 | 409 (номер занят), 422 |
| GET | `/equipment` | Список предметов | 200 | — |
| GET | `/equipment/{id}` | Один предмет | 200 | 404, 422 |
| POST | `/loans` | Выдать предмет сотруднику | 201 | 404, 409, 422 |
| GET | `/loans?active=&employee_id=` | Список выдач с фильтрами | 200 | 422 |
| GET | `/loans/{id}` | Одна выдача | 200 | 404, 422 |
| POST | `/loans/{id}/return` | Вернуть предмет | 200 | 404, 409 (уже возвращена) |

Ошибки приходят в виде `{"detail": "текст"}`. Ошибки валидации (422) формирует FastAPI.

Примеры тел запросов:

```json
POST /employees   {"name": "Иван", "email": "ivan@example.com"}
POST /equipment   {"name": "Ноутбук", "inventory_number": "INV-001"}
POST /loans       {"employee_id": 1, "equipment_id": 1}
```

Пример ответа на выдачу:

```json
{"id": 1, "employee_id": 1, "equipment_id": 1,
 "issued_at": "2026-11-18T04:10:00.123456+03:00", "returned_at": null}
```

Тексты ошибок 409: «Оборудование уже выдано», «У сотрудника уже три активные выдачи», «Сотрудник неактивен», «У сотрудника есть активные выдачи», «Выдача уже возвращена».

### Полный сценарий

1. `POST /employees` — создать сотрудника (получаем `id`).
2. `POST /equipment` — создать предмет (получаем `id`).
3. `POST /loans` с этими `id` — выдача, `returned_at` пустое.
4. `GET /loans?active=true` — выдача в списке активных.
5. `POST /loans/{id}/return` — возврат, `returned_at` заполнено.
6. `GET /loans?active=false` — выдача в списке завершённых.

## Устройство проекта

```
app/
  main.py          приложение, подключение роутеров, обработчики ошибок, /health
  database.py      подключение к PostgreSQL
  dependencies.py  внедрение зависимостей, транзакция запроса
  exceptions.py    NotFoundError, ConflictError
  routers/         HTTP: маршруты, коды ответов
  schemas/         Pydantic-схемы запросов и ответов
  services/        бизнес-правила (не знают про HTTP)
  repositories/    SQL (не делают commit/rollback)
tests/
  fakes.py         фейковые репозитории в памяти
  conftest.py      фикстуры
  test_services/   тесты сервисов
  test_api/        тесты HTTP-слоя
schema.sql         схема БД
```

- **Роутер** тонкий: принимает запрос, вызывает сервис, возвращает результат.
- **Сервис** хранит бизнес-правила и бросает `NotFoundError` / `ConflictError`. Он зависит не от конкретных классов репозиториев, а от `Protocol`, поэтому в тестах вместо БД подставляются фейки.
- **Репозиторий** выполняет только SQL. Параметры передаются через `%s`, склейки строк и f-строк в SQL нет.
- `main.py` превращает `NotFoundError` в 404 и `ConflictError` в 409.

### Граница транзакции

На один HTTP-запрос открывается одно соединение, общее для всех репозиториев (`get_conn` в `dependencies.py`). Если обработчик завершился без ошибок, делается `commit`, при исключении `rollback`, в конце соединение закрывается. Всё это происходит до отправки ответа клиенту. Репозитории сами никогда не вызывают `commit` и `rollback`, поэтому многошаговая операция (например, выдача: проверки и вставка) атомарна.

### Защита от гонок

- Строка сотрудника блокируется `SELECT ... FOR UPDATE` при выдаче и деактивации, строка выдачи при возврате. Блокировка держится до конца общей транзакции.
- Второй активный предмет в выдаче невозможен благодаря частичному уникальному индексу `uq_loans_active_equipment` (`WHERE returned_at IS NULL`).
- Ограничения БД: `NOT NULL`, `UNIQUE` на email и инвентарный номер, `CHECK` (непустые строки, `returned_at >= issued_at`), внешние ключи `ON DELETE RESTRICT`.

## Тесты

```bash
mypy app tests --disallow-untyped-defs
python -m pytest -v
```

- === 82 passed in 0.16s ===

Тесты запускаются без PostgreSQL: в сервисных тестах репозитории заменены фейками, в API-тестах через `app.dependency_overrides` подменяются сервисы. Они проверяют бизнес-правила, коды ответов, валидацию и обработку ошибок. Работу самой базы (ограничения, блокировки, откат) фейки не проверяют, это сделано вручную на настоящей PostgreSQL (см. ниже).

CI (GitHub Actions, `.github/workflows/tests.yml`) на каждый push и pull request запускает mypy и pytest.

## Ручные проверки на PostgreSQL

| № | Проверка | Результат |
|---|---|---|
| 1 | Данные переживают перезапуск API | После остановки и запуска `uvicorn` `GET /loans` возвращает созданную выдачу |
| 2 | Вторая активная выдача предмета прямым SQL | Отклонена: `23505 duplicate key ... uq_loans_active_equipment`. Вставка без `issued_at` отклонена: `23502 NOT NULL` |
| 3 | Повторная выдача после возврата | У предмета две строки: старая с заполненным `returned_at`, новая активная. Индекс частичный, возврат его освобождает |
| 4 | Откат незавершённой операции | Создал сотрудника в транзакции, до `commit` бросил исключение и сделал `rollback`. Внутри транзакции запись видна (1), из другого соединения до `commit` не видна (0), после отката нет (0) |
| 5 | Блокировка на двух соединениях | Окно A: `BEGIN; SELECT ... WHERE id = 1 FOR UPDATE;`. Окно B с таким же запросом ждёт и продолжает сразу после `COMMIT` в окне A |
| 6 | Уникальность email и инвентарного номера | Дубль email: `23505 employees_email_key`. Дубль номера: `23505 equipment_inventory_number_key` |
| 7 | Гонка при создании с одинаковым email | Два вызова `create` с одной почтой: второй отклонён базой и превращён в `ConflictError` |

## Как закрыты замечания предыдущей работы

- ID принимаются как строгие целые (`strict`): `true`, `1.5`, `"1"` дают 422, значения вне диапазона `1..2147483647` тоже.
- Длины строк в схемах соответствуют ограничениям БД.
- Время выдачи и возврата ставит сервер (`now()`), клиент передать его не может (`extra="forbid"`). Формат дат в ответах ISO 8601.
- Во всём проекте добавлена типизация, `mypy app tests --disallow-untyped-defs` проходит без ошибок.
